## 一、为什么选这个工具集

### 1.1 起点项目本身是经过验证的

it-tools 是一个被大量开发者日常使用的开源工具集合，客观数据（2026-09-28 通过 GitHub API 实测）：

| 指标 | 数值 |
|---|---|
| Star 数 | **40,706** |
| Fork 数 | **5,447** |
| 仓库体积 | 13,707 KB ≈ **13.4 MB** |
| 内置工具 | **90 个** |
| 技术栈 | Vue 3 + TypeScript + Vite + Pinia + Naive UI + UnoCSS |
| 许可 | **GPL-3.0** |
| 最近提交 | 2026-09-27（活跃维护） |

**选择它的三个理由：**

**第一，架构决定了「加一个工具」的成本极低。** 项目采用「一个工具 = 一个目录」的组织方式，每个工具只需三样东西：

```
src/tools/your-tool/
├── index.ts        # 注册信息：名称、路径、描述、关键词、图标
├── your-tool.vue   # 界面
└── your-tool.models.ts  # 纯逻辑（可选，便于写测试）
```

注册机制是静态 import 后加入分类数组，没有复杂的插件系统、没有运行时约定。项目自带脚手架命令 `pnpm script:create:tool`，甚至能在 30 秒内生成骨架。这意味着**我们的创新成本可以集中投在「工具本身好不好用」上，而不是和框架搏斗**。

**第二，技术栈是纯前端，天然契合「离线可用」和「隐私安全」。** 项目没有任何后端服务，所有运算都在浏览器里完成，构建产物是静态文件。这让我们要做的离线能力（PWA）不需要额外改造架构，只需要正确配置。

**第三，本土化空间是真实存在的。** 上游的简体中文语言包（`locales/zh.yml`）已经存在，但 90 个工具的受众定位是「开发人员和 IT 工作者」，对普通学生来说大量工具用不上。我们要做的是**在保留通用工具的前提下，把面向学生的场景补上**——这是上游不会做、也不该做的事。

### 1.2 为什么不从零写一个

从零写意味着重新实现 90 个工具中那些已经稳定的部分（编码转换、哈希、JSON 处理、二维码等），这是纯粹重复劳动。基于成熟项目二次开发，把精力集中在真正的差异化点上，是更诚实也更高效的选择。

代价是必须接受 GPL-3.0 的开源义务 —— 这一点我们在第五章专门讨论，并且**主动把它当作优势而非负担**。

## 二、我们加了什么，解决了什么真实问题

### 2.1 核心原创工具：公文格式自检

#### 真实问题

高校学生组织（社团、学生会、团委、班级）每学期都要产出大量公文：活动通知、工作请示、策划方案、总结报告、表彰决定。这些材料在提交给指导老师、学院或学校办公室时，**格式合规是硬门槛**：

- 字号不对 → 退回重排
- 层级序号写成 `1.` 而不是 `1．` → 退回
- 成文日期写 `2026年10月1日` 而不是 `二〇二六年十月一日` → 退回
- 发文字号写 `校团字[2026]第005号` 而不是 `校团字〔2026〕5 号` → 退回

**关键在于：这些错误极其琐碎，但极其常见，而且没有经验的人根本不知道规则在哪。** GB/T 9704-2012《党政机关公文格式》是 30 多页的国家标准，没有学生会为了写一份招新通知去通读它。结果就是「写 → 被退回 → 问老师 → 改 → 再被退回」的反复消耗。

我们访谈过的那类典型场景是：**一份 800 字的通知，格式问题要来回改 3 到 4 轮，累计消耗数小时**，而这些时间本可以用在内容上。

#### 现有方案为什么不够

| 现有方案 | 问题 |
|---|---|
| 百度搜索「公文格式规范」 | 拿到一堆零散条文，还要自己对号入座，无法定位到自己文档哪一行错了 |
| 学校发的《公文格式规范》Word 文档 | 静态文档，不能校验；要靠人眼逐条比对 |
| 问有经验的学长学姐 | 依赖个人，经验不可复制，且对方也未必记得全 |
| 通用文档校对工具 | 只查错别字和语法，完全不懂公文的版式规范 |
| 同类的「公文格式检查」网页 | 极少，且大多只提供一个输入框把规范条文列出来，本质还是人工比对 |

**核心缺口：没有人做「自动读你的文档 → 告诉你哪一段哪一处违反了哪一条规则 → 并给出修改方法」。**

#### 我们做了什么

一个**能读真实排版参数**的公文格式校验器，实现 14 条规则、8 个维度的检查：

**检查维度全覆盖：**

| 类别 | 检查内容 |
|---|---|
| 页面设置 | 页边距（上 37 mm、下 35 mm、左 28 mm、右 26 mm）、纸张规格 |
| 字体字号 | 标题方正小标宋 2 号、正文仿宋_GB2312 3 号、一级标题黑体、二级标题楷体_GB2312 |
| 段落格式 | 行距 28 磅、首行缩进 2 字符 |
| 版头 | 发文字号六角括号「〔〕」、不写「第」字、顺序号不编虚位 |
| 主体 | 标题字体字号、成文日期汉字写法、附件说明格式 |
| 层级序号 | 一、→（一）→ 1．→（1）四级规范，识别半角点号、顿号误用 |
| 标点符号 | 中英文标点混用、括号配对与全角 |
| 用语规范 | 口语化用词、数字用法 |

**技术上的两个关键突破：**

**突破一：能读到文档内部的真实排版参数。**

这是与所有同类工具最本质的区别。`.docx` 文件本质上是一个 zip 包，正文在 `word/document.xml`，排版信息以 OOXML 格式存储。我们自己实现了一个最小可用的 zip 读取器（支持 STORE 与 DEFLATE 两种压缩方式，用浏览器原生的 `DecompressionStream` 解压，不引入任何第三方库），再用 `DOMParser` 解析 XML，从中提取：

- `w:rFonts` → **真实的字体名**（中文 `eastAsia`、西文 `ascii`）
- `w:sz` → **真实的字号**（单位为半磅，除以 2 得到磅值）
- `w:spacing` → **真实的行距**（区分 `exact` 固定值与 `auto` 倍数，分别按不同公式换算）
- `w:ind` → **真实的首行缩进**（`firstLine` 为 twip 单位，按字号换算成字符数）
- `w:pgMar` / `w:pgSz` → **真实的页边距与纸张规格**（twip 换算毫米：1 英寸 = 1440 twip = 25.4 mm）

**因此我们能说出「第 3 段正文使用宋体五号，规范要求仿宋_GB2312 三号」这种话**，而不是含糊的「请检查字体」。这是纯前端网页工具里很少见的能力。

**突破二：区分「能自动修的」和「必须手动调的」。**

很多工具在这里犯的错误是：发现问题后假装自己能修，或者干脆不区分。

我们的做法是：
- **文本类问题**（标点、序号、日期写法、发文字号）→ 直接在文本上做安全替换，并给出**修复前后的逐行对照**，用户确认后才应用
- **版式类问题**（字体、字号、行距、页边距）→ **不偷偷改动**，而是生成**具体的 Word 操作路径**，例如：
  > 选中正文 → 右键段落 → 行距选「固定值」，设置值填 28 磅；段前段后间距均设 0。

这个区分很重要：**让用户清楚地知道「哪部分已经被解决了，哪部分还需要我动手」，而不是给一个虚假的「已修复」按钮。**

**修复引擎的谨慎设计：**

自动修复只处理**确定无歧义**的写法，绝不猜测内容。几个例子：

- 中文后的半角逗号 `,` → 全角 `，`，但**英文和数字内部的标点不动**
- 中文后的半角冒号 `:` → 全角 `：`，但**用负向断言排除时间格式** `12:30`
- 中文后的半角句点 `.` → 句号 `。`，但**排除小数和英文缩写**
- `1.` → `1．`（全角点号），但**只在行首匹配**，避免破坏版本号
- `1、` → `1．`（顿号误用），同样**限定行首**
- `二零二六` → `二〇二六`（年份用「〇」不用「零」）
- **`弄虚作假` 这类固定搭配主动保护** —— 「弄」在口语中是问题词，但在这个成语里是规范用语，所以要先剔除固定搭配再判断

这些细节决定了工具是「能放心用」还是「不敢用」。我们的原则是：**宁可漏报，不可误改。**

**闭环验证结果：**

用内置的示例公文（故意植入多处典型错误）实测完整流程：

| 阶段 | 得分 | 问题数 | 硬性违规 | 建议改进 |
|---|---|---|---|---|
| 修复前 | **50** | 16 | 6 | 10 |
| 一键修复后 | **97** | 1 | 0 | 1 |

自动化验证的 6 项关键行为全部通过：固定搭配保护、三级序号全角化、顿号序号修正、日期汉字化、时间格式不破坏、中文句点转换。剩余 1 项是示例文档中刻意保留的半角冒号，属于规则正常捕获。

**格式得分的计算方式（不是随便拍的）：**

- 硬性违规每处扣 8 分，建议改进每处扣 3 分，提示每处扣 1 分
- **同一规则重复命中时边际递减**：第 1 处全额扣分，之后每处按 50% 计
  - 这样设计的理由：一篇 20 段正文全是宋体，不应该比只有 1 段出错扣 20 倍的分 —— 因为**修复动作是同一个**（全选改字体），成本不随段落数线性增长

### 2.2 第二个原创工具：课表冲突检测与空闲时段

#### 真实问题

两个具体场景：

**场景一：冲突不可见。** 教务处选课系统只告诉你「这门课在哪、什么时候」，**不会告诉你两门课撞了**。学生要自己拿两张课表用眼睛比对。更麻烦的是「部分重叠」—— 比如 A 课 08:00-10:00、B 课 09:00-11:00，重叠 1 小时，这种在教务系统上看起来是两门独立的课，但实际无法同时上。

**场景二：约时间成本极高。** 社团要开例会、小组要做课题讨论、想约人一起自习 —— 这些都需要找到**多个人共同的空闲时间**。现在的做法是：把几个人的课表截图发到群里，然后大家用眼睛找。4 个人就是 4 张课表的交叉比对，**这个任务用人眼做既慢又容易漏**。

#### 现有方案为什么不够

- 教务系统：只负责展示课程，不做冲突分析和空闲计算
- 手机日历 App：需要手动录入每一节课，录入成本高于收益
- 大学生课表类 App：绝大多数需要注册登录、有的还要付费，且**普遍不支持多人时间求交**
- 手动比对：慢、易错、无法处理多人场景

#### 我们做了什么

**功能一：冲突检测，区分严重程度。**

不是简单地说「有冲突」，而是区分：
- **完全重叠（exact）**：两门课时间完全相同 → 这通常意味着选课异常或重修记录未清理，需要立刻联系教务
- **部分重叠（partial）**：给出**具体的重叠分钟数**，提示可能需要与任课教师沟通调课

同时，**不同人的课程之间不判冲突**（这是多人场景的必要设计），首尾相接的时间段不算冲突（08:00-09:40 与 09:40-11:20 是正常的连堂）。

**功能二：空闲时段计算。**

在用户设定的作息范围内（默认 08:00–22:00），自动算出所有空闲区间。关键实现细节：

- **先合并重叠的课程区间，再求补集** —— 否则重叠课程会产生错误的空闲段
- **支持最短时长过滤** —— 默认过滤掉 30 分钟以下的碎片时间，因为 20 分钟的空档实际无法用来做任何事
- 课程跨越作息边界时不会产生负时长

**功能三：多人课表求交集（这是最有价值的差异点）。**

用户把每个人的课表分别粘贴进来（支持多人分别录入），工具直接算出**所有人都空闲**的时段，并推荐最长的那一段。这是同类工具普遍缺失的能力。

**场景价值：** 一个 5 人的社团管理层要开例会，原本需要 5 张课表人工比对，现在 30 秒出结果。

**功能四：排课建议。**

自动生成可行动的建议，例如：
- 「周五课业最重，共 3.7 小时课程，建议不要把社团例会安排在这一天。」
- 「空闲时段共 8 段，最长的一段是周二 09:40–22:00，适合安排例会或小组讨论。」
- 「按天看，周二空闲最多（12.3 小时），是最容易约到人的一天。」

**课表录入的零门槛设计：**

要求用户手动填表是反人性的 —— 录入成本一旦超过收益，工具就不会被使用。所以我们支持**直接粘贴教务系统的课表文本**，并且兼容两种常见格式：

```
格式 A（逐行时间）：
周一 08:00-09:40 高等数学 教三201

格式 B（节次写法）：
周三 3-4节 线性代数 教二105
```

解析器还会自动提取**地点**和**周次**（`1-16周`），并兼容「周一/星期一/礼拜一/Mon」多种写法。节次格式会按常见大学作息自动换算成时间。

**无法识别的行不会被静默丢弃**，而是逐行报告「第 N 行未识别到星期」，避免用户以为课表已经全部录入。

**实测验证（真实教务课表格式）：**

```
输入 7 门课（含 1 组刻意植入的冲突）
→ 解析成功 7 门，失败 0 行
→ 冲突检测：1 组，正确判定为「完全重叠」硬冲突
→ 空闲时段：8 段（周一 11:40-22:00 / 周二 09:40-22:00 / 周三 08:00-13:30, 15:10-22:00 …）
→ 统计：每周课时 13.7 小时，最忙周五 3.7 小时
→ 边界测试（重叠课程合并）：通过
```

### 2.3 中文本地化

上游已有简体中文语言包，我们在其基础上做了三件事：

1. **新增工具的中文命名与描述**——按学生实际搜索习惯撰写。关键词同时收录中文与拼音，**搜「公文」「gongwen」「发文字号」「格式」都能命中**，解决了中文输入法下不知道该怎么搜的问题。
2. **新增「校园常用」分类并置于首位**——让高频工具出现在首页第一屏，而不是埋进「开发」「网络」这类面向程序员的分类里。
3. **界面文案按国内高校语境调整**——使用「教务」「社团」「例会」「学院」等词，而非直译的「调度」「会议」。

### 2.4 离线可用

**这是被校园网络环境倒逼出来的需求。** 教学楼、图书馆、宿舍在特定时段网络极不稳定，很多在线工具在这些时刻直接不可用。

实现方式：

- 基于 `vite-plugin-pwa` + Workbox 配置 Service Worker，静态资源全部预缓存
- 配置 Web App Manifest，支持**安装到桌面**，之后独立窗口打开
- 快捷方式直达两个高频工具（公文自检、课表工具）
- **离线状态显式提示** —— 用一个状态条明确告诉用户「当前离线，功能不受影响」，而不是让用户怀疑工具是不是坏了

**为什么离线方案对本项目特别成立：所有工具都是纯前端运算，不发任何网络请求。** 因此离线不是「降级体验」，而是**功能完全等同**。这一点是很多依赖后端 API 的在线工具做不到的。

### 2.5 隐私保护（顺带但重要）

公文往往包含未公开的活动安排、人员名单、内部决策；课表包含个人作息。把这些文件上传到第三方网站处理是有风险的。

本项目的所有解析和检查**全部在浏览器本地完成**，文档内容不出设备。这一点在界面上明确告知用户，并且在实际实现中确实如此（无任何 fetch 上传逻辑）。

**这构成了对「网页版在线工具」的信任优势** —— 同类工具若采用服务端处理，用户无法验证文档是否被留存。

## 三、怎么让同学用起来

工具做得再好，没人用等于零。我们的推广路径分四步：

### 3.1 第一步：找到最小的验证场景（第 1 个月）

不做广撒网，先**锁定 1 个学生组织深度使用** —— 我们所在的协会本身就是最理想的验证对象。

- 让协会的**公文写作**全流程接入这个工具，记录每次使用发现的问题
- 收集「工具没检查出来但老师退回了的」案例 → 反过来扩充规则库
- 收集「工具报了但其实是误报」的案例 → 修正规则，避免过度报警消耗信任

**这一阶段的核心指标不是用户量，而是规则准确率。** 一个误报率高的检查工具会迅速失去信任。

### 3.2 第二步：横向铺开到院系（第 2–3 个月）

- 面向**各学院的学生会、团委、社团负责人**做一次 15 分钟的演示
- 重点不是讲技术，而是**现场演示一个真实案例**：拿一份被退回过的通知，当场跑出问题清单
- 提供现成的**内嵌代码**（一个 iframe 或独立部署），让各院系可以挂在自己的站点上
- 制作一页纸的**速查卡**：最常见的 8 个格式错误 + 一键检查入口

### 3.3 第三步：把工具变成流程的一部分（第 3–6 个月）

推广能否持久，取决于工具是否嵌入了**既有流程**，而不是多了一个需要记住的网址。

- **嵌入公文提交环节**：与指导老师约定，公文提交时把「检查报告」一并附上（工具支持一键导出 Markdown 报告），让「先自检」成为习惯
- **嵌入社团培训**：把公文格式作为新成员培训的一个环节，用这个工具做现场练习
- **变成开学季的固定动作**：每年招新、换届时，公文量激增，是自然的使用高峰

### 3.4 第四步：开源带来的外部扩散（持续）

因为项目以 GPL-3.0 开源，**其他高校可以直接部署自己的实例**，只需要改校名和规范细节。这是一个低成本的自然扩散路径：

- 在 GitHub 上维护清晰的部署文档和中文化说明
- 提供「另一个学校要改哪几处」的移植清单
- 欢迎其他学校提交他们自己的规范差异（Pull Request）

**这不是设想，而是已经在技术层面准备好的一件事**：规则集是数据驱动的（`RULES` 数组），新增一所学校的特殊规范只需增加规则条目，不需要改动引擎。

### 3.5 推广中要避开的坑

| 坑 | 我们的对策 |
|---|---|
| 装成官方工具，被认为代表学校 | 明确声明「非官方工具，检查结果仅供参考，不能替代学校办公室的正式审核」 |
| 过度承诺准确率 | 每个规则都标注**规范依据原文**，让用户能自己判断，而不是盲信分数 |
| 一次性推广后无人维护 | 建立问题反馈入口，规则库持续迭代 |
| 只讲技术不讲场景 | 推广材料一律以「你被退回过吗」开头，不从技术架构讲起 |

## 四、技术方案

### 4.1 整体架构

```
校园工具箱（纯静态站点）
├── 保留 it-tools 原有 90 个工具
│   └── 通过静态注册表 src/tools/index.ts 统一管理
├── 新增「校园常用」分类（置于首位）
│   ├── 公文格式自检
│   │   ├── official-document.rules.ts    规则引擎（14 条规则）
│   │   ├── official-document.parser.ts   文档解析器（含 zip/OOXML 解析）
│   │   ├── official-document.fixer.ts    一键修复与报告生成
│   │   └── *.spec.ts                     单元测试
│   └── 课表冲突与空闲时段
│       ├── timetable-conflict.models.ts  冲突检测 + 空闲计算 + 文本解析
│       ├── multi-person-planner.vue      多人求交集组件
│       └── *.spec.ts                     单元测试
├── PWA 离线层（Service Worker + Manifest）
└── 中文语言包（locales/zh.yml）
```

**架构原则：逻辑与界面分离。** 所有核心算法都写在独立的 `.ts` 文件里，不依赖 Vue 运行时。这带来三个好处：

1. **可测试** —— 纯函数可以直接写单元测试，不需要挂载组件
2. **可复用** —— 其他学校想接入自己的系统时，可以直接引用逻辑层
3. **可验证** —— 我们能够脱离浏览器完整验证引擎行为（本次开发中正是这么做的）

### 4.2 规则引擎的可扩展设计

规则是**声明式**的，每条规则包含编号、类别、严重度、标题、依据、检查函数：

```ts
{
  id: 'FMT-010',
  category: '字体字号',
  severity: 'error',
  title: '正文字体或字号不符合规范',
  basis: 'GB/T 9704-2012 7.3.1：公文正文一般用 3 号仿宋体字…',
  check: (doc) => [/* 返回违规项数组 */],
}
```

新增规则只需在 `RULES` 数组登记，**不需要改动引擎、界面或报告生成逻辑**。违规项支持携带「段号 + 字符区间 + 原文片段」，界面据此做定位高亮。

**这让「不同学校有不同规范」这件事变成配置问题而非开发问题。**

### 4.3 为什么用纯前端而非服务端

| 维度 | 纯前端方案 | 服务端方案 |
|---|---|---|
| 隐私 | 文档不出设备，可验证 | 文档需上传，用户无法验证 |
| 离线 | 功能完全等同 | 断网即不可用 |
| 部署成本 | 静态文件，任何 CDN / 校内服务器均可 | 需要服务器、运维、成本 |
| 可移植 | 其他学校 clone 即可自建 | 需要重新部署后端 |
| 性能 | 无网络往返 | 依赖网络延迟 |

**结论：本项目所有需求都指向纯前端。** 唯一需要服务端的情形是「跨设备同步」，而那与「隐私优先」的定位冲突，故明确不做。

## 五、GPL-3.0 合规：理解与应对

**这是本项目必须讲清楚的一部分，也是我们主动选择透明的部分。**

### 5.1 传染性意味着什么

GPL-3.0 是**强 copyleft（传染性）许可**。对本项目而言，核心约束是：

> **只要你在原项目基础上修改并对外分发，你的修改成果也必须以 GPL-3.0 授权并公开源代码。**

关键在于「**分发（conveying）**」的定义。把网页部署到公网、让同学访问，**构成分发**。因此：

| 行为 | 是否需要开源 |
|---|---|
| 下载源码，自己电脑上跑，自己用 | **不需要**（GPL-3.0 第 2 条：仅为自身使用不构成传播） |
| 改完只在校内内网部署，访问者仅限同一法人单位成员 | 通常**不构成**向公众传播 |
| **部署到公网给同学用** | **必须开源**，且必须以 GPL-3.0 |
| 把修改版打包成闭源产品对外发布 | **禁止** |
| 只改个名字就当作自己原创闭源项目 | **禁止** |

### 5.2 我们的态度：把它当优势，不当负担

很多学生项目在这里会犯两个错误：要么无视许可偷偷闭源（法律风险），要么因为「必须开源」而放弃选这个项目。

**我们的判断是：开源对本项目是加分项，理由有三：**

1. **它让成果可以被复制到其他高校。** 我们要解决的问题（公文格式、课表冲突）是**全国高校普遍存在**的，不是我们学校特有的。GPL 保证了任何一个学校都能自由部署、按自己的规范修改 —— 这恰恰让项目的社会价值最大化。

2. **它约束了「占为己有」的诱惑。** 双创比赛的评审看重真实贡献。上游有 4 万 Star、90 个工具，如果我们把整个仓库包装成自己的原创成果，本质上是不诚实的。**主动、清晰地划出「哪些是上游的、哪些是我们做的」，反而最能体现项目的诚信与技术判断力。**

3. **它倒逼我们做好工程规范。** 要开源，就必须有清晰的目录结构、可读的代码、完整的文档、可运行的测试。这些要求会把项目质量整体抬上去。

### 5.3 我们具体做了什么

**已落实的合规动作：**

| 措施 | 实现 |
|---|---|
| 保留原许可证 | `LICENSE` 文件保留 GPL-3.0 原文，未作修改 |
| 保留版权声明 | 保留原项目版权归属信息 |
| **明确的修改声明** | 新增 `NOTICE.md`，逐文件列出「哪些是新增的、哪些是修改的、哪些保持原样」 |
| 本项目整体以 GPL-3.0 发布 | `package.json` 中 `license` 字段为 `GNU GPLv3` |
| 源码获取途径 | 若公开部署，站点内提供源码仓库入口 |
| 不使用原项目商标 | 采用独立名称「校园工具箱 / Campus Toolbox」，不暗示获得原作者背书 |
| 界面内明示 | 生成的检查报告页脚注明「本工具基于 it-tools（GPL-3.0）二次开发，依据 GPL-3.0 同样以 GPL-3.0 授权」 |

**给使用者的一句话说明（写在 README 与 NOTICE 里）：**

> 如果希望以闭源方式使用，唯一的合法路径是**不使用原项目代码、从零实现**，而不是修改本项目后再闭源。

### 5.4 学术诚信角度的说明

本项目是**开源二次开发**，不是原创项目。在比赛材料、答辩、文档中，我们都会明确：

- **上游贡献**：it-tools 项目、90 个原有工具、Vue 3 技术栈与整体架构（40,706 Star，贡献者众多）
- **本项目贡献**：2 个原创工具（含 1 套规则引擎、1 个 docx 解析器）、中文本地化增强、离线能力配置、文档与合规实践

**我们主张的价值在于「把通用工具集改造成解决具体校园场景的产品」，而不是「从零发明了这些工具」。** 这个定位是诚实的，也是经得起追问的。

## 七、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **规则误报**消耗用户信任 | 高 | 每条规则标注规范依据；宁可漏报不可误改；建立快速反馈修正通道 |
| 用户不知道规范原文，盲信分数 | 中 | 每条违规都展示依据条文原文；明确声明「仅供参考，不替代正式审核」 |
| 学校规范与国标有差异 | 中 | 规则集数据驱动，可按学校定制；文档中说明可配置 |

| 推广后无人维护 | 中 | 开源 + 清晰贡献指南，降低他人接手的门槛 |

## 八、总结

**这个项目要解决的问题很朴素：** 学生在校期间有大量高频、琐碎、容易出错、又没人教你规则的事情 —— 公文格式对不对、课表有没有撞、几个人的空闲时间在哪。这些事单件消耗不大，但**累积起来是真实的效率损耗**。

**我们的做法也很朴素：** 不去发明新概念，而是拿一个已经被 4 万人验证过的工具集，把它从「服务开发者的通用工具箱」改造成「服务学生的校园工具箱」，并在这个过程中做到三件上游没做的事 —— **能读真实排版参数的公文校验、支持多人求交的课表工具、以及断网也能用的离线能力**。

**而 GPL-3.0 的传染性不是障碍，是设计的一部分：** 因为必须开源，所以其他高校可以自由部署；因为必须开源，所以我们不能含糊自己做了什么、没做什么；因为必须开源，这个解决普遍问题的工具才能真正被普遍使用。
